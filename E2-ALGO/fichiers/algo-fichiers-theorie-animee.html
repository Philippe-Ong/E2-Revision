01
l'idée

main reçoit un tableau de chaînes, pas des nombres

Un programme lancé depuis un terminal reçoit ses arguments sous deux paramètres : argc, le nombre de mots, et argv, un tableau de pointeurs vers ces mots. Tout arrive en texte ; la conversion en nombre est à la charge du programme.

args.c
#include <stdio.h>

int main(int argc, char *argv[])
{
    for (int i = 0; i < argc; i++) {
        printf("This is Argument number %d - %s\n", i, argv[i]);
    }
    printf("argv[argc] == NULL : %d\n", argv[argc] == NULL);
    return 0;
}
console — Algo-cmdLine.exe Hello World!
This is Argument number 0 - Algo-cmdLine.exe
This is Argument number 1 - Hello
This is Argument number 2 - World!
argv[argc] == NULL : 1

Le découpage est fait par le shell avant le lancement : un espace sépare deux arguments, sauf entre guillemets. Le programme ne voit jamais la ligne d'origine, seulement les mots déjà séparés.

La règle

char *argv[] dans une liste de paramètres est exactement char **argv : un pointeur vers un tableau de pointeurs vers char. argv[i] est donc une chaîne, argv[i][0] son premier caractère, et argv[argc] vaut NULL.

Convertir et vérifier

L'énoncé 2.1 demande atof. Cette fonction ne signale aucune erreur : atof("abc") vaut 0.0, et atof("12abc") vaut 12.0. strtod fait la même conversion mais laisse un pointeur sur le premier caractère non consommé, ce qui permet de refuser l'argument.

conversion.c
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char *argv[])
{
    if (argc != 2) { return 1; }
    char *fin = NULL;
    double v = strtod(argv[1], &fin);
    if (fin == argv[1] || *fin != '\0') {   /* rien lu, ou reste du texte */
        printf("invalide : \"%s\"\n", argv[1]);
        return 1;
    }
    printf("valeur = %g\n", v);
    return 0;
}

Le piège

atof("abc") vaut 0.0 : impossible de distinguer une saisie fautive d'un vrai zéro. Avec atof, la validation de l'énoncé 2.1 ne peut pas être correcte. strtod fournit la position d'arrêt ; c'est elle qui décide.

02
formats

printf écrit des valeurs, scanf lit des adresses

Les deux fonctions partagent la même chaîne de format et les mêmes spécificateurs, mais pas la même convention d'appel : printf reçoit les valeurs, scanf reçoit les adresses de ces valeurs. Un & oublié est l'erreur la plus fréquente du chapitre.

printf.c
printf("[%-4d]\n", -13);          /* [-13 ]       largeur 4, à gauche  */
printf("[%5d]\n", -13);           /* [  -13]      largeur 5, à droite  */
printf("[%08d]\n", 13);           /* [00000013]   remplissage par 0    */
printf("[% 8d]\n", 13);           /* [      13]   espace pour le signe */
printf("[%.3f]\n", 3.14);         /* [3.140]      trois décimales      */
printf("[%8.2f]\n", -3.14159);    /* [   -3.14]                        */
printf("[%g] [%g]\n", 0.0001, 1234567.0);  /* [0.0001] [1.23457e+06]   */
printf("[%x] [%s] [%c]\n", 254, "Olympia", 'A');  /* [fe] [Olympia] [A] */

int n = printf("Hello world %d !\n", 2047);   /* affiche, n vaut 19 */

Le retour dit ce qui s'est passé

printf renvoie le nombre de caractères écrits, ou une valeur négative en cas d'échec. scanf renvoie le nombre d'affectations réussies, 0 si l'entrée ne correspond pas au format, et EOF si la fin de fichier survient avant toute conversion. La diapositive 16 écrit que scanf renvoie « le nombre total de caractères écrits » : c'est la définition de printf, pas celle de scanf.

retours.c
#include <stdio.h>

int main(void)
{
    int n = printf("Hello world %d !\n", 2047);   /* n = 19 */
    unsigned int number = 0;
    int lus = scanf("%u", &number);               /* 1, 0 ou EOF */
    printf("printf : %d, scanf : %d, number : %u\n", n, lus, number);
    return 0;
}

La règle des adresses

Pour scanf, chaque argument est l'adresse de la variable à remplir : &n pour un int, &d pour un double, nom (sans &) pour un tableau de char, puisque son nom est déjà une adresse. Un double se lit avec %lf, jamais %f.

Le piège

scanf("%d", x) avec int x : gcc le signale (format '%d' expects argument of type 'int *', but argument 2 has type 'int') et, si on l'ignore, le programme écrit à l'adresse contenue dans x — comportement indéfini. scanf("%f", &d) sur un double est refusé de la même façon : c'est %lf.

Pourquoi scanf("%s", nom) est-il dangereux même avec un &nom[0] correct ?
Parce que %s n'a pas de limite : la fonction écrit autant de caractères que l'utilisateur en fournit. Il faut une largeur, %19s pour un char nom[20]. Vérifié : avec %19s et 26 caractères tapés, seuls 19 sont stockés et le reste demeure dans le tampon.
03
lire une ligne

scanf lit un mot, fgets lit une ligne

Trois outils, trois contrats. scanf convertit selon un format et laisse tout ce qu'il n'a pas consommé. fgets lit jusqu'au '\n' ou jusqu'à remplir le tampon, et conserve le '\n'. getline lit une ligne de longueur quelconque en allouant la mémoire.

fgets.c
#include <stdio.h>
#include <string.h>

int main(void)
{
    char ligne[8];
    while (fgets(ligne, sizeof ligne, stdin) != NULL) {
        size_t n = strlen(ligne);
        printf("lu=%lu, dernier=%s\n", (unsigned long)n,
               (n > 0 && ligne[n-1] == '\n') ? "\\n" : "autre");
    }
    return 0;
}
console — deux lignes tapées, la seconde plus longue que le tampon

lu=7, dernier=autre
lu=6, dernier=\n

La deuxième ligne fait 13 caractères : fgets en garde 7 et s'arrête, sans '\n'. L'appel suivant lit la fin de la même ligne, 89012\n. C'est le comportement attendu, et c'est aussi ce qui permet de détecter une saisie trop longue : si strchr(ligne, '\n') renvoie NULL, la ligne n'était pas complète et il faut vider le tampon.

ligne.c
char ligne[64];
if (fgets(ligne, sizeof ligne, stdin) != NULL) {
    char *p = strchr(ligne, '\n');
    if (p != NULL) { *p = '\0'; }        /* enlever le saut de ligne */
    printf("ligne=[%s]\n", ligne);
}
Vider le tampon

La diapositive 17 fournit la fonction du cours : void clrstdin(void) { int ch; while ((ch = getchar()) != '\n' && ch != EOF) { } }. Elle consomme tout ce qui reste sur la ligne courante. Sans elle, une saisie fautive laisse les caractères en place et la lecture suivante échoue immédiatement.

    Le piège

    fgets garde le '\n' ; scanf("%s") ne le garde jamais ; gets a été retiré du C11 parce qu'il ne peut pas être borné. Après un fgets, toute comparaison de chaîne doit tenir compte de ce '\n', sinon "-l\n" n'est pas égal à "-l".

Son intérêt : la ligne peut faire 10 000 caractères, la fonction réalloue le tampon et renvoie sa longueur.

    04
    le modèle

    Un flux est une suite d'octets ; FILE* en est le descripteur

    Toutes les entrées/sorties du C passent par des streams : une séquence de caractères organisée en lignes terminées par '\n'. Trois flux existent avant main — stdin, stdout, stderr — et fopen en fabrique d'autres.

    À retenir

    Écrire dans un flux, c'est remplir un tampon ; le disque ne voit les octets qu'au vidage. Ce décalage est la raison d'être de fflush et la source de bien des « le fichier est vide alors que le programme a écrit ».

    ouvrir.c
    #include <stdio.h>

int main(void)
{
    FILE *f = fopen("notes.txt", "r");
    if (f == NULL) {
        perror("notes.txt");        /* notes.txt: No such file or directory */
        return 1;
    }
    /* ... lecture ... */
    if (fclose(f) != 0) {           /* rend le tampon, ferme le descripteur */
        perror("fclose");
        return 1;
    }
    f = NULL;
    return 0;
}

    Texte ou binaire sous Windows

    En mode texte, '\n' est traduit en \r\n à l'écriture : fputs("abc\n", f) produit 5 octets en mode "w" et 4 en mode "wb". Pour compter des octets ou déplacer un curseur, ouvrir en binaire.

    Le piège

    La diapositive 24 ferme pFile même quand fopen a renvoyé NULL, parce que le fclose est hors du else. fclose(NULL) est un comportement indéfini. Le test de NULL doit couvrir toutes les utilisations du pointeur, fermeture comprise.

    05
    lecture texte

    fgets renvoie une ligne ou NULL, jamais autre chose

    Lire un fichier texte revient à répéter une lecture jusqu'à ce qu'elle échoue. Trois fonctions le font à trois niveaux : fgetc un caractère, fgets une ligne, fscanf des valeurs formatées. La fin de fichier n'est pas une valeur : c'est un indicateur, consultable après coup.

    lire-lignes.c
    #include <stdio.h>

int main(void)
{
    FILE *f = fopen("notes.txt", "r");
    if (f == NULL) { perror("notes.txt"); return 1; }

    char ligne[256];
    while (fgets(ligne, sizeof ligne, f) != NULL) {
        fputs(ligne, stdout);        /* le '\n' est déjà dans ligne */
    }
    if (ferror(f)) { perror("lecture"); }

    fclose(f);
    return 0;
}
    caracteres.c
    int c;
while ((c = fgetc(f)) != EOF) {     /* un octet à la fois */
    putchar(c);
}

int valeur;
while (fscanf(f, "%d", &valeur) == 1) {   /* valeurs formatées */
    printf("%d\n", valeur);
}

    La règle

    La boucle correcte teste le retour de la lecture : while (fgets(...) != NULL), while ((c = fgetc(f)) != EOF), while (fscanf(...) == 1). feof ne sert pas à piloter la boucle : il ne devient vrai qu'après une lecture qui a échoué.

    Le piège

    while (!feof(f)) { fgets(ligne, sizeof ligne, f); printf("[%s]", ligne); } affiche la dernière ligne deux fois. Au dernier tour, feof est encore faux, fgets renvoie NULL sans modifier ligne, et printf réaffiche le contenu précédent.

      écriture texte

      Écrire, c'est remplir un tampon ; fflush ou fclose le vident

      Les fonctions d'écriture ne touchent pas le disque à chaque appel : elles remplissent un tampon associé au flux. Le fichier ne reçoit les octets qu'au vidage, quand le tampon est plein, sur fflush, ou à la fermeture.

      Les écritures et leurs retours
      appelécritretouréchec
      fprintf(f, fmt, ...)du texte formaténombre de caractèresvaleur négative
      fputs(s, f)une chaîne, sans le '\0'valeur non négativeEOF
      fputc(c, f)un caractèrele caractère écritEOF

      ecrire.c
      #include <stdio.h>

int main(void)
{
    FILE *f = fopen("mesures.csv", "w");     /* crée ou tronque */
    if (f == NULL) { perror("mesures.csv"); return 1; }

    fprintf(f, "%d;%s;%.1f\n", 1, "mesure", 23.5);
    fputs("fin\n", f);
    fputc('#', f);
    fflush(f);                                /* les octets partent maintenant */

    fclose(f);                                /* vide le reste et ferme */
    return 0;
}
      Mesure

      Avec un tampon non vide : avant fflush, un second fopen en lecture sur le même fichier ne voit 0 octet ; après fflush, il voit les 9 octets de ligne un\n. Après fclose, les deux lignes sont présentes, soit 20 octets. La taille du tampon dépend de l'implémentation (4096 octets en général).

      Le piège

      fopen("f.txt", "w") tronque un fichier existant à zéro octet dès l'ouverture. Pour ajouter sans effacer, c'est "a". Et un programme qui se termine par exit() ou un plantage sans fclose perd le contenu du tampon, pas le fichier lui-même.

        binaire

        Un enregistrement binaire, c'est sizeof octets contigus

        Un fichier binaire ne contient pas de lignes : il contient les octets des objets, tels quels. Un enregistrement occupe sizeof octets — bourrage compris — et le n-ième commence à n × sizeof. fseek place le curseur, ftell le lit.

        binaire.c
        #include <stdio.h>
#include <stddef.h>

struct Mesure { int id; double valeur; };

int main(void)
{
    struct Mesure m1 = {1, 23.5};
    struct Mesure m2 = {2, 24.0};
    struct Mesure m3 = {0, 0.0};

    FILE *f = fopen("mesures.bin", "wb");
    if (f == NULL) { perror("mesures.bin"); return 1; }
    fwrite(&m1, sizeof m1, 1, f);          /* 1 élément de 16 octets */
    fwrite(&m2, sizeof m2, 1, f);
    printf("apres 2 fwrite : ftell = %ld\n", ftell(f));   /* 32 */

    fclose(f);
    f = fopen("mesures.bin", "rb");
    if (f == NULL) { perror("mesures.bin"); return 1; }

    fseek(f, (long)sizeof(struct Mesure), SEEK_SET);      /* 2e enregistrement */
    printf("apres fseek : ftell = %ld\n", ftell(f));      /* 16 */

    size_t n = fread(&m3, sizeof m3, 1, f);              /* 1 élément lu */
    printf("%lu lu : id=%d, valeur=%.1f, ftell=%ld\n",
           (unsigned long)n, m3.id, m3.valeur, ftell(f)); /* 1, 2, 24.0, 32 */
    fclose(f);
    return 0;
}

        fseek(f, off, SEEK_CUR)relative à la position courante0, ou non nul

        La règle

        fwrite(ptr, size, count, f) écrit count éléments de size octets et renvoie le nombre d'éléments écrits, pas le nombre d'octets. fread renvoie le nombre d'éléments lus : inférieur à count en fin de fichier ou en cas d'erreur, et c'est feof/ferror qui distingue les deux.

        Le piège

        sizeof(struct Mesure) vaut 16, pas 12 : les quatre octets de bourrage font partie de l'enregistrement. Calculer fseek(f, 12, ...) à la main place le curseur au milieu de valeur. Et un fichier binaire doit être ouvert avec "b", sinon Windows traduit les octets 0x0A en 0x0D 0x0A et le fichier est corrompu.

          Chaque appel dit s'il a réussi, et deux indicateurs disent pourquoi

          Le C ne lève pas d'exception : une fonction d'entrée/sortie signale l'échec par sa valeur de retour. feof et ferror distinguent ensuite une fin de fichier normale d'une vraie erreur, et errno porte le code du système, que perror traduit.

          erreurs.c
          #include <stdio.h>

int main(void)
{
    FILE *f = fopen("absent.txt", "r");
    if (f == NULL) {
        perror("absent.txt");       /* absent.txt: No such file or directory */
        return 1;                   /* ne pas appeler fclose sur NULL      */
    }

    char ligne[256];
    while (fgets(ligne, sizeof ligne, f) != NULL) { /* ... */ }

    if (ferror(f)) {                 /* vraie erreur, pas une fin de fichier */
        perror("lecture");
    } else if (feof(f)) {
        printf("fin de fichier atteinte\n");
    }
    clearerr(f);                     /* remet les deux indicateurs à zéro */
    fclose(f);
    return 0;
}
          Mesure

          Lire dans un flux ouvert en écriture seulement (fopen("vide.txt", "w") puis fgetc) renvoie EOF et laisse ferror(f) non nul. clearerr remet l'indicateur à zéro ; l'erreur elle-même n'est pas réparée.

          La règle

          errno n'a de sens qu'immédiatement après l'appel qui a échoué : tout autre appel de bibliothèque peut l'écraser. perror(prefixe) écrit prefixe: message système sur stderr, avec le errno courant.

          Le piège

          feof et ferror sont collants : une fois positionnés, ils le restent jusqu'à clearerr, rewind ou une nouvelle ouverture. Un fseek réussi efface l'indicateur de fin de fichier, mais pas celui d'erreur ; clearerr efface les deux et ne répare rien.

          Ex2.6 : afficher un fichier, avec ou sans numéros de ligne

          L'énoncé demande trois choses : ouvrir un fichier texte dont le nom vient de la ligne de commande, l'afficher ligne par ligne avec fgets, et numéroter les lignes si l'option -l est présente. Le format d'appel est Algo-Ex2_6-DisplayFileContents <filename> [-l].

          ex2-6.c
          #include <stdio.h>
#include <string.h>

int main(int argc, char *argv[])
{
    if (argc < 2 || argc > 3) {
        printf("Usage : %s <fichier> [-l]\n", argv[0]);
        return 1;
    }
    int numeroter = (argc == 3 && strcmp(argv[2], "-l") == 0);

    FILE *f = fopen(argv[1], "r");
    if (f == NULL) {
        perror(argv[1]);
        return 1;
    }

    char ligne[256];
    unsigned long no = 0;
    while (fgets(ligne, sizeof ligne, f) != NULL) {
        no++;
        if (numeroter) {
            printf("%4lu  %s", no, ligne);   /* le '\n' vient de ligne */
        } else {
            fputs(ligne, stdout);
        }
    }
    if (ferror(f)) {
        perror("lecture");
        fclose(f);
        return 1;
    }
    fclose(f);
    return 0;
}

          Ex2.1 et Ex2.4 : convertir, valider, calculer

          Les deux exercices font la même chose par deux entrées différentes : l'un reçoit ses opérandes en arguments, l'autre les lit au clavier. Dans les deux cas, la difficulté n'est pas l'opération — c'est la validation de ce qui entre.

          Ex2.1 — calculatrice en ligne de commande

          Format demandé : Algo-Ex2_1-CommandLine <Arg1> <Op> <Arg2>, avec Op parmi + − x /. La fonction getResult prend les deux opérandes et l'opérateur ; la validation est faite avant l'appel, dans une fonction séparée.

          ex2-1.c
          #include <stdio.h>
#include <stdlib.h>
#include <string.h>

static int parametresValides(int argc, char *argv[])
{
    if (argc != 4) { return 0; }
    if (strlen(argv[2]) != 1) { return 0; }
    char op = argv[2][0];
    return (op == '+' || op == '-' || op == 'x' || op == '/');
}

static int nombreValide(const char *texte, double *valeur)
{
    char *fin = NULL;
    *valeur = strtod(texte, &fin);
    return (fin != texte && *fin == '\0');
}

static double getResult(double a, char op, double b)
{
    switch (op) {
        case '+': return a + b;
        case '-': return a - b;
        case 'x': return a * b;
        case '/': return a / b;
        default:  return 0.0;      /* inatteignable : déjà validé */
    }
}

int main(int argc, char *argv[])
{
    double a = 0.0;
    double b = 0.0;
    if (!parametresValides(argc, argv)
        || !nombreValide(argv[1], &a)
        || !nombreValide(argv[3], &b)) {
        printf("Usage : %s <Arg1> <Op> <Arg2>   (Op = + - x /)\n", argv[0]);
        return 1;
    }
    if (argv[2][0] == '/' && b == 0.0) {
        printf("Division par zero.\n");
        return 1;
    }
    double r = getResult(a, argv[2][0], b);
    printf("%g %c %g = %g\n", a, argv[2][0], b, r);
    return 0;
}

          Signature et erreurs

          getResult renvoie un double : elle ne peut pas signaler une erreur. La division par zéro et les arguments invalides sont donc traités avant l'appel, dans main. C'est la raison d'être de parametresValides et nombreValide : chacune répond par oui ou non.

          Ex2.4 — deux opérandes au clavier

          L'énoncé demande une fonction qui affiche le texte d'invite, lit la valeur avec scanf et la retourne convertie, plus le traitement d'erreur. Une variante rend le succès explicite : la fonction renvoie un statut et écrit la valeur par pointeur.

          ex2-4.c
          #include <stdio.h>
#include <stdlib.h>

/* 1 si la lecture a réussi, 0 sinon */
static int lireOperande(const char *invite, double *valeur)
{
    printf("%s", invite);
    fflush(stdout);                 /* l'invite n'a pas de '\n' */
    if (scanf("%lf", valeur) != 1) {
        int c;
        while ((c = getchar()) != '\n' && c != EOF) { }  /* vider la ligne */
        return 0;
    }
    return 1;
}

int main(void)
{
    double a = 0.0;
    double b = 0.0;
    if (!lireOperande("Please enter first operand: ", &a)
        || !lireOperande("Please enter second operand: ", &b)) {
        fprintf(stderr, "Valeur invalide.\n");
        return 1;
    }
    printf("Result of %.5f + %.5f = %.5f\n", a, b, a + b);
    return 0;
}
          console — saisie 1.2 puis 3.45
          Please enter first operand: 1.2
Please enter second operand: 3.45
Result of 1.20000 + 3.45000 = 4.65000

          La sortie reprend le format de l'énoncé : cinq décimales, donc %.5f. Avec %f seul, on obtiendrait 1.200000, six décimales.

          Le piège

          Sans fflush(stdout), l'invite peut ne pas s'afficher avant la lecture : stdout est tamponné ligne par ligne, et l'invite ne finit pas par '\n'. À l'écran, on voit alors le curseur clignoter sans savoir quoi taper. Sur une saisie abc, scanf renvoie 0 et laisse abc\n dans le tampon ; sans le vidage, la seconde lecture échoue aussi.

          Pourquoi scanf("%lf", valeur) et non scanf("%lf", &valeur) dans cette fonction ?
          valeur est déjà un double * : c'est l'adresse fournie par l'appelant. Ajouter & donnerait un double **, refusé par le format.

          Le piège du chemin

          "notes.txt" est relatif au dossier courant du processus, pas à celui du source ni de l'exécutable. Lancer le programme depuis un autre dossier change le fichier ouvert. En cas de doute : perror affiche le nom utilisé et le message système.

          Le piège du mode

          fopen en "w" tronque à l'ouverture, avant la première écriture. Un test qui ouvre puis échoue laisse déjà un fichier vide. Pour vérifier l'existence sans détruire, ouvrir en "r".

          Un programme écrit 4 octets, puis se termine par return 1 sans fclose. Le fichier contient-il les 4 octets ?
          Pas garanti : les octets sont dans le tampon du flux. Un return depuis main ferme normalement tous les flux ouverts, donc le tampon est vidé ; un plantage ou _exit ne le fait pas. La règle sûre reste fclose explicite, avec vérification du retour.

          Les réflexes

          • Tout fopen est suivi d'un test de NULL.
          • Tout fopen a son fclose, sur chaque chemin de sortie.
          • Toute lecture est testée par son retour, jamais par feof.
          • scanf reçoit des adresses ; un double se lit avec %lf.
          • %s a toujours une largeur, ou est remplacé par fgets.
          • Le '\n' de fgets est retiré avant toute comparaison.
          • Un fichier binaire s'ouvre en "rb" ou "wb".
          • Le déplacement se calcule en sizeof, jamais à la main.
          • Un argument de ligne de commande est validé avant conversion.
          • Les messages d'erreur vont sur stderr.
