La carte : tout a une adresse, rien n'est magique

Avant d'écrire une ligne de code, il faut savoir ce qu'on pilote : un processeur 32 bits, de la mémoire, et des périphériques qui répondent à des adresses.

L'idée

Un microcontrôleur n'est pas « un petit ordinateur ». C'est une puce unique où le processeur, la mémoire et les périphériques (ports, timers, UART…) partagent le même espace d'adressage. Écrire à l'adresse d'un périphérique, c'est déjà le piloter : il n'y a pas d'appel système entre toi et le matériel.

Le cœur est un Cortex-M4F : 32 bits, architecture Harvard (bus d'instructions et de données séparés), jeu RISC, jusqu'à 120 MHz. Attention au QCM : « RISC » décrit le jeu d'instructions ; la case attendue pour l'organisation mémoire est Harvard.

Les registres qui expliquent les appels de fonction

Un appel de fonction n'est pas une abstraction : c'est un saut avec une adresse de retour. R13 = SP pointe la pile, R14 = LR garde l'adresse de retour, R15 = PC désigne la prochaine instruction. PRIMASK et BASEPRI masquent les interruptions.

  1. L'instruction d'appel range l'adresse de retour dans LR.
  2. PC prend l'adresse de la fonction appelée.
  3. La fonction empile ce qu'elle doit préserver, en descendant SP.
  4. Au retour, PC reprend la valeur de LR — une ISR revient exactement de la même façon.

D'où viennent les 120 MHz

L'oscillateur interne bat à 16 MHz. La PLL multiplie jusqu'à 480 MHz (le VCO), puis un diviseur ramène l'horloge système à 120 MHz. Un seul appel règle tout et renvoie la fréquence réellement obtenue : c'est cette valeur qu'on garde, jamais une constante recopiée à la main.

HAL_TM4C1294.c
uint32_t g_sysClockHz;                        /* fréquence réellement obtenue */

void clockInit(void)
{
    g_sysClockHz = SysCtlClockFreqSet(SYSCTL_OSC_INT | SYSCTL_USE_PLL
                                   | SYSCTL_CFG_VCO_480, 120000000);
}
Pourquoi ce détour

Parce que tout le reste en dépend : le SysTick compte des cycles de cette horloge, les délais se calculent avec elle, et la charge du processeur se mesure en temps réel. Une horloge fausse rend faux tous les calculs de la page 5.

Quelle broche allume D1 ? Et quel niveau lit-on sur PJ0 quand USR_SW1 est appuyé ?
D1 = PN1 (D2 = PN0 : l'ordre est inversé). Les boutons sont actifs bas : appuyé ⇒ niveau logique 0, ce qui explique le pull-up interne.

gpio · exercice 1.1

Parler au matériel : trois étapes, puis des masques

Allumer une LED suppose de réveiller le port, de choisir le sens de la broche, puis de régler son étage électrique. DriverLib fait chaque étape en un appel — encore faut-il les appeler dans l'ordre.

L'idée

Une broche GPIO est un interrupteur que le logiciel lit ou commande. Mais une broche appartient à un port, et un port ne répond pas tant que son horloge n'est pas allumée. C'est la première cause de « ça ne fait rien » chez un débutant.

Les trois étapes

  1. Horloge du port : SysCtlPeripheralEnable(SYSCTL_PERIPH_GPIOx), puis attendre SysCtlPeripheralReady. Sans horloge, l'accès au port provoque une faute.
  2. Direction : GPIOPinTypeGPIOInput(port, broches) ou GPIOPinTypeGPIOOutput.
  3. Étage électrique : GPIOPadConfigSet(port, broches, courant, type). Pour un bouton, GPIO_PIN_TYPE_STD_WPU (pull-up) ; pour une LED, GPIO_STRENGTH_6MA. Sur une entrée, seul le type compte.
La règle

Un masque, pas un numéro. GPIO_PIN_0 vaut 0x01, GPIO_PIN_1 vaut 0x02, et on combine par |. GPIOPinWrite(port, broches, valeur) n'écrit que les bits du masque ; GPIOPinRead rend un masque (0x02), pas 1.

interruptions · exercice 1.2

Être prévenu : l'ISR note, main traite

Une interruption renverse le rapport au temps : ce n'est plus le programme qui surveille, c'est le matériel qui appelle. Encore faut-il que la fonction appelée soit courte et qu'elle acquitte sa cause.

L'idée

En polling, tu vas sans cesse voir si le facteur est passé. Avec une interruption, il sonne : tu poses ce que tu fais, tu ouvres, puis tu reprends exactement là où tu t'étais arrêté. L'ISR (Interrupt Service Routine) est la fonction qui « ouvre la porte » — elle note l'événement, main() fait le travail.

Le NVIC décide, et « plus petit » veut dire « plus urgent »

Le TM4C a 3 bits de priorité, soit 8 niveaux (0 à 7). Ces bits occupent le poids fort de l'octet : le niveau n s'écrit n << 5. Une interruption plus prioritaire qu'une ISR en cours la coupe ; de priorité égale ou plus basse, elle reste pending.

Le piège de QCM

La priorité 0 est la plus haute — « plus faible = moins important » est faux. Et IntPrioritySet(INT_GPIOJ, 2) ne donne pas le niveau 2 : les bits bas sont ignorés, il reste le niveau 0. Il faut écrire 2 << 5 (0x40) ; le niveau 5 s'écrit 0xA0.

Une ISR propre, et le code de l'exercice 1.2

  • Signature imposée : void f(void). Ni attente active, ni printf dans l'ISR.
  • Lire la cause, acquitter tôt, publier l'événement, sortir.
  • Toute variable partagée avec main est volatile ; « lire puis effacer » se fait en section critique (IntMasterDisable / IntMasterEnable).

static volatile ButtonEvent_t usrSw1Event = eBUTTON_NO_EVENT;   /* main lit, ISR écrit */

static void button_ISR(void)
{
    uint32_t const st = GPIOIntStatus(GPIO_PORTJ_BASE, true);
    if (st & eBUTTON_USR_SW1) {
        GPIOIntClear(GPIO_PORTJ_BASE, eBUTTON_USR_SW1);           /* acquitter TÔT */
        usrSw1Event = buttonState(eBUTTON_USR_SW1) ? eBUTTON_EVENT_PRESSED
                                                   : eBUTTON_EVENT_RELEASED;
    }
    /* idem SW2 */
}

ButtonEvent_t HAL_Button_Event(Button_t b)      /* lit ET efface, en section critique */
{
    ButtonEvent_t ev;
    IntMasterDisable();
    ev = (b == eBUTTON_USR_SW1) ? usrSw1Event : usrSw2Event;
    if (b == eBUTTON_USR_SW1) usrSw1Event = eBUTTON_NO_EVENT;
    else                      usrSw2Event = eBUTTON_NO_EVENT;
    IntMasterEnable();
    return ev;
}

Les trois verrous à ouvrir, dans l'ordre : la source dans le périphérique (GPIOIntEnable), l'IRQ dans le NVIC (IntEnable, fait par GPIOIntRegister), puis le masque global (IntMasterEnable). Après un reset, les interruptions sont désactivées.

Deux IRQ sont en attente, niveaux 1 et 3. Laquelle passe ? Et si la 3 arrive pendant l'ISR de la 1 ?
La 1 (plus petit = plus prioritaire). La 3 reste pending et ne passe qu'à la fin de l'ISR de la 1 : seule une priorité strictement plus haute préempte.

Ne rien perdre : le tampon entre l'ISR et main

Un Event-Flag ne retient qu'un événement. Dès que deux appuis se suivent, le second écrase le premier. La FIFO est la réponse : une file où l'ISR dépose et où main retire, chacun à son rythme.

L'idée

Une FIFO (First In, First Out) est une file d'attente : premier arrivé, premier servi. Le tableau ne bouge jamais : seuls deux index avancent en tournant. L'ISR produit, main consomme — et l'ordre des événements est conservé.

Les deux conditions à écrire sans hésiter

SerialBuffer.c
bool SerialBuffer_isEmpty(SerialBuffer_t *b) { return b->rd == b->wr; }
bool SerialBuffer_isFull(SerialBuffer_t *b)  { return (b->wr + 1) % N == b->rd; }

bool SerialBuffer_addData(SerialBuffer_t *b, char c)          /* producteur : l'ISR */
{   if (SerialBuffer_isFull(b)) { b->lost++; return false; }
    b->data[b->wr] = c;                   /* ÉCRIRE d'abord…            */
    b->wr = (b->wr + 1) % N;              /* …puis avancer l'index      */
    return true; }

bool SerialBuffer_getData(SerialBuffer_t *b, char *c)         /* consommateur : main */
{   if (SerialBuffer_isEmpty(b)) return false;
    *c = b->data[b->rd];                  /* LIRE d'abord…               */
    b->rd = (b->rd + 1) % N;              /* …puis avancer l'index       */
    return true; }
La règle

Écrire la donnée avant d'avancer l'index : sinon main peut voir l'index à jour et lire une case pas encore écrite. Un seul producteur et un seul consommateur : inutile de bloquer les interruptions.

Dimensionner : le seul calcul qui tombe à tous les coups

La FIFO doit absorber tout ce qui arrive entre deux passages de main. On calcule le débit en octets par seconde, puis le volume pendant l'attente, puis la taille en puissance de 2.

La formule

Q = (bauds / 10) × T, puis N − 1 ≥ ⌈Q⌉ et N = 2ᵏ. Le 10 vient de la trame 8N1 : 1 start + 8 données + 1 stop. T est l'intervalle entre deux lectures.

Pourquoi 16 et pas 10

« Minimum » ne veut pas dire « juste au-dessus du volume » : il faut 10 cases utiles, donc N ≥ 11, et une taille en puissance de 2 donne 16. Écris les trois lignes du calcul — ce sont elles qui rapportent les points.

La pile, et le tampon qui change de mode

Une pile (LIFO) n'a qu'un index, top : −1 pour vide, N−1 pour plein. Empiler avance puis écrit (data[++top] = c), dépiler lit puis recule (c = data[top--]). Et surtout : N cases contiennent N éléments — pas de case perdue.

Exemple d'école : empiler « desserts » puis tout dépiler donne « stressed ». Même boucle, deux lectures différentes selon le mode : c'est tout l'intérêt du buffer configurable.

Faire plusieurs choses : un métronome dans le cœur

Une seule interruption périodique suffit à donner une notion de temps à l'application. Le SysTick ne fait rien lui-même : il dépose un événement, et la boucle principale décide.

L'idée

Le SysTick est un compteur 24 bits décroissant, intégré au cœur, exception n° 15. Il décompte de N−1 à 0, lève l'interruption, puis recommence. Tu règles le tempo avec N — et N se calcule, il ne s'invente pas.

La formule

N = fclk × T, avec 1 ≤ N ≤ 2²⁴ = 16 777 216. À 120 MHz : 100 ms donnent 12 000 000 cycles, soit un RELOAD de 11 999 999. Au-delà de 2²⁴ cycles — 139,81 ms à 120 MHz — une seule période est impossible.

La charge du processeur : ce que chaque source emprunte

Chaque interruption prend un peu de temps au processeur. Additionne ce que toutes prennent en une seconde : tu obtiens la part du temps occupé. Il faut U < 1, sinon des interruptions se perdent.

La formule

U = Σ fi · di : chaque source i réveille fi fois par seconde une ISR de durée di. Les occupations s'additionnent, quel que soit l'ordre de service.

Le piège

Le corrigé 2025 annonce 24 ms sur 60 ms (40 %) : il oublie CAN et UART. À une question ouverte, écris la somme des quatre sources (47 %) et signale l'écart. Autre piège : SysTickEnable() lance le compteur, c'est SysTickIntEnable() qui autorise l'interruption.

Mesurer, pas supposer

Une durée se mesure avec le compteur lui-même : SysTickValueGet() avant et après, puis écoulé = début − fin (modulo N), parce que le compteur décroît. À 120 MHz, 3 000 ticks valent 25 µs.

Pour le temps de traitement d'une boucle, on lève une broche GPIO au début de main et on la baisse à la fin, puis on lit l'analyseur logique. Attention : le temps écoulé n'est pas le temps CPU propre — une interruption peut s'insérer entre les deux.

Veille

Sans veille, la boucle tourne à 100 % en testant la FIFO — et une LED qui clignote ne prouve pas le contraire. Quand la FIFO est vide, MAP_SysCtlSleep() endort le cœur jusqu'à la prochaine interruption autorisée. Le préfixe MAP_ est obligatoire sur ce microcontrôleur.

Attention à l'ordre : « vérifier puis dormir » n'est pas atomique. Un événement arrivé entre le test et l'endormissement est traité au tick suivant — un retard, pas une perte.

Peut-on obtenir 250 ms en une seule période à 120 MHz ?
Non : 250 ms demandent 30 000 000 cycles, au-delà de 2²⁴ (139,81 ms). Prends une base de 50 ms (N = 6 000 000) et compte 5 ticks dans l'ISR.

Structurer : une couche ne parle qu'à celle du dessous

L'ISR du bouton doit prévenir l'application. Si elle l'appelle directement, la HAL dépend de main.c : plus de portabilité, ni pour l'une ni pour l'autre. La solution tient en un pointeur.

L'idée

Une fonction a une adresse, exactement comme une variable. Un pointeur de fonction garde cette adresse : on peut la changer pendant l'exécution, la ranger dans un tableau, puis appeler « la fonction qui est là ». L'application confie l'adresse d'une de ses fonctions à la HAL, qui l'appellera le moment venu : c'est un callback.

Boutons : les rebonds, et pourquoi on ne branche pas tout sur l'interruption

Un bouton mécanique rebondit : un seul appui produit une rafale de fronts en quelques millisecondes, et chaque front peut déclencher une interruption. Deux stratégies tiennent la route :

  • ISR minuscule + FIFO : l'ISR dépose un événement, main filtre et agit.
  • Polling filtré : échantillonner à intervalle fixe et valider après n lectures identiques — charge bornée, recommandé par le corrigé.
anti-rebond par polling (principe du cours)
bool lireBoutonFiltre(Button_t b)
{
    bool etat = buttonState(b);                  /* première lecture        */
    for (uint8_t i = 0; i < 3; i++) {              /* 3 confirmations         */

Le piège

Alterner une LED s'écrit count = (count + 1) % 2. Le corrigé 2024 écrit ++count % 2 : la variable est modifiée deux fois dans la même expression, c'est un comportement indéfini que gcc -Wall signale. Et l'en-tête fourni fait foi : ledWrite, pas HAL_Led_Write.

Pourquoi le pointeur du callback doit-il être static dans le module HAL ?
Une variable locale disparaît à la sortie de la fonction d'enregistrement : l'ISR ne retrouverait plus l'adresse. La static du module vit pendant tout le programme et reste privée au module.

Comment un octet devient un nombre

Un octet n'est qu'une suite de 8 bits : c'est le type qui dit comment la lire. Le même 0xF6 vaut 246 en non signé et −10 en signé. En complément à deux, l'opposé s'obtient en inversant les bits puis en ajoutant 1.

−10 sur 8 bits+10 = 0x0A → 1111 0101 → +1 = 1111 01100xF6
−5 sur 8 bits+5 = 0x05 → 1111 1010 → +1 = 1111 10110xFB
