01
définition

Une fonction qui s'appelle elle-même, avec une porte de sortie

Le cours définit une fonction récursive de deux façons : elle s'appelle elle-même, ou elle fait partie d'une séquence d'appels qui revient sur elle (func1 → func2 → func_n → func1). Dans les deux cas, la même question se pose : où l'enchaînement s'arrête-t-il ?

À retenir

Résoudre un problème de taille n en réutilisant la solution du même problème sur une taille plus petite. La récursion n'est pas une répétition : c'est une réduction. Il faut donc deux pièces, et elles vont toujours ensemble : un cas de base que l'on sait résoudre sans récursion, et un cas récursif qui rapproche du cas de base.

Les trois conditions d'une récursion correcte

Le cours énonce les conditions pour qu'un problème se prête à une fonction récursive. Elles servent aussi de grille de lecture d'un code qu'on ne connaît pas :

  • Un ou plusieurs cas simples ont une solution triviale — 0! = 1, un disque se déplace en un coup, une liste d'une personne n'a personne à prévenir.
  • Les autres cas se redéfinissent en termes de problèmes plus proches des cas simples — n! = n × (n−1)!, déplacer n disques ramène à n−1.
  • Le problème se réduit effectivement, appel après appel : la taille décroît strictement, sinon la récursion ne s'arrête jamais.
multiplication.c
/* diapo 6 : multiplier, c'est additionner n fois */
uint32_t mult(uint32_t n, uint32_t m)
{
    if (n == 1u) {                 /* cas simple : plus rien à ajouter */
        return m;
    }
    return m + mult(n - 1u, m);    /* réduction : n -> n - 1 */
}
/* mult(3, 5) = 5 + mult(2, 5) = 5 + (5 + mult(1, 5)) = 5 + 5 + 5 = 15 */

La règle

Une fonction récursive sans condition d'arrêt empile des trames sans jamais les dépiler : la pile est épuisée et le programme s'arrête (stack overflow). Ce n'est pas une boucle infinie qui tourne : c'est un plantage immédiat.

Combien d'appels de mult pour mult(5, 7) ?
Cinq appels : mult(5,7), mult(4,7), mult(3,7), mult(2,7), mult(1,7). Le dernier est le cas de base et rend 7 ; les quatre retours ajoutent 7 à chaque fois, soit 35. Le nombre d'appels vaut n, pas n−1.
02
la pile d'appels

Chaque appel empile une trame, chaque retour la dépile

Une fonction ordinaire reçoit ses paramètres dans des registres et rend la main. Une fonction récursive ne peut pas faire cela : quand elle s'appelle, l'appel en cours n'est pas fini, il attend un résultat. Tout ce qu'il doit retrouver après l'appel est donc rangé dans une trame (stack frame) posée sur la pile.

L'adresse de retour est la pièce décisive : c'est elle qui dit à l'appelant où reprendre quand la valeur arrive. Sans elle, la machine saurait calculer Fact(3) mais pas quoi faire du 3 qu'il rend.

Sens de la pile

Sur x86 et ARM, la pile descend en mémoire : chaque nouvelle trame est placée à une adresse plus petite. Dans les laboratoires, les adresses baissent donc de 0x7ffc30 vers 0x7ffbf0 à mesure que la pile monte. Une trame occupe quelques dizaines d'octets, parfois plus si la fonction a de grands tableaux locaux.

Le piège

Croire que la valeur « remonte » comme une donnée stockée quelque part. Ce qui remonte, c'est le retour de fonction : la trame du sommet est détruite, sa valeur est copiée dans la trame du dessous, qui reprend son calcul. Une trame détruite ne peut plus être lue : c'est pour cela qu'on ne retourne jamais l'adresse d'une variable locale.

03
étude de cas · Ex 1.2

La factorielle : même résultat, deux chemins

La factorielle est la définition récursive la plus courte du cours : n! = n × (n−1)! avec 0! = 1. L'exercice 1.2 demande trois implémentations du même calcul — itération, récursion, table précalculée — pour comparer trois façons de coder, pas trois résultats.

factorielle.c
/* a) itération : une boucle descend de n jusqu'à 2 */
uint64_t Factorial_with_iteration(uint32_t number)
{
    uint64_t result = 1u;
    for (uint32_t i = number; i >= 2u; i--) {
        result *= (uint64_t)i;
    }
    return result;
}

/* b) récursion : la fonction s'appelle elle-même */
uint64_t Factorial_with_recursion(uint32_t number)
{
    if (number <= 1u) {                 /* cas de base : 0! = 1! = 1 */
        return 1u;
    }
    return (uint64_t)number * Factorial_with_recursion(number - 1u);
}

Les deux versions font le même nombre de multiplications : n−1 pour n ≥ 2, aucune pour 0 et 1. Elles diffèrent par ce qu'elles engagent en plus : la récursive ouvre n trames, l'itérative garde deux variables.

La règle

Les deux versions sont en O(n) : le nombre d'opérations est proportionnel à n. La récursive paie en plus n appels de fonction et n trames, l'itérative seulement deux variables. Sur un petit n, la différence ne se mesure pas ; sur un million, elle décide du plantage.

Jusqu'où le type tient

Le résultat grandit beaucoup plus vite que n. La note du cours insiste sur les types : uint32_t pour le paramètre, uint64_t pour le résultat, %llu pour l'affichage. Voici les bornes réelles, recalculées :

La dernière factorielle exacte en 64 bits est donc 20!. Au-delà, aucune récursion ne sauve le résultat : le problème est le type, pas l'algorithme. C'est pour cela que la version LUT de l'exercice refuse l'indice 21 et rend 0.

Les deux pièges de la factorielle

La base oubliée ou fausse. if (number == 0) au lieu de number <= 1 fonctionne pour 0, mais reste correct pour 1 ; en revanche une base if (number == 1) seule boucle à l'infini pour 0. Écrire number <= 1 couvre les deux cas triviaux et ne peut pas être franchi vers le négatif — impossible ici, uint32_t oblige.

Le débordement silencieux. 21! ne provoque aucune erreur : le produit dépasse 2⁶⁴ et repart à zéro. Le seul signe est un résultat absurde.

Pourquoi (uint64_t)number devant le produit ?
number est un uint32_t. Sans conversion, le compilateur peut calculer number * ... dans un type plus étroit avant de l'affecter au uint64_t. Le transtypage force la multiplication en 64 bits et évite de perdre les bits hauts dès que le produit dépasse 32 bits.
04
étude de cas · Ex 1.10

Hanoï : deux fois le travail du niveau précédent

Trois aiguilles, n disques de tailles différentes empilés sur la première. Il faut les amener sur la deuxième, en ne déplaçant qu'un disque à la fois et sans jamais poser un grand sur un petit. Le cours pose la question avant de donner la solution : combien de coups ?

À retenir

Pour déplacer n disques de la source vers la destination, il faut d'abord déplacer les n−1 plus petits sur l'aiguille auxiliaire, puis déplacer le plus grand — un seul coup —, puis ramener les n−1 sur la destination. Le problème de taille n se ramène à deux problèmes de taille n−1 et un coup.

hanoi.c
/* ex 1.10 : récursif, avec le compteur passé par adresse */
void toh(uint32_t disk, char source, char dest, char aux, uint32_t *pMoves)
{
    if (disk == 1u) {                   /* cas simple : un seul disque */
        printf("Move disk 1 from %c to %c\n", source, dest);
        (*pMoves)++;
        return;
    }
    toh(disk - 1u, source, aux, dest, pMoves);   /* n-1 vers l'auxiliaire */
    printf("Move disk %u from %c to %c\n", disk, source, dest);
    (*pMoves)++;
    toh(disk - 1u, aux, dest, source, pMoves);   /* n-1 vers la destination */
}

L'appel toh(3, 'A', 'B', 'C') produit exactement les sept lignes de l'énoncé, dans cet ordre : 1 A→B, 2 A→C, 1 B→C, 3 A→B, 1 C→A, 2 C→B, 1 A→B. Ce n'est pas un ordre choisi : c'est celui que la récursion impose.

La règle · le nombre de coups

M(1) = 1 et M(n) = 2·M(n−1) + 1. En déroulant : M(n) = 2ⁿ − 1. Pour n = 3 : 7 coups ; pour n = 10 : 1 023 ; pour n = 20 : 1 048 575 ; pour les 64 disques de la légende : 18 446 744 073 709 551 615.

La profondeur n'est pas le problème

Pour 64 disques, la pile ne contient que 64 trames : aucun risque de débordement. Ce qui bloque, c'est le nombre de coups, en O(2ⁿ). Hanoï est le cas typique d'un algorithme dont le temps explose alors que la mémoire reste linéaire.

Le compteur en variable globale

Une variable globale uint32_t gMoves fonctionne, mais la fonction dépend alors d'un état caché : deux appels successifs ne repartent pas de zéro, et la fonction n'est plus réentrante. L'énoncé demande explicitement de l'éviter. On passe uint32_t *pMoves et on incrémente (*pMoves)++ : l'appelant décide où vit le compteur.

diviser pour régner · loterie · Ex 1.14

Diviser pour régner : la loterie et l'alerte téléphonique

Donald a gagné à la loterie et doit prévenir les quinze membres de sa famille par téléphone. Chacun applique la même consigne : couper sa liste en deux, appeler la première personne de chaque moitié, et lui confier cette moitié. C'est du diviser pour régner — un problème de taille n devient deux problèmes de taille n/2.

La consigne du cours

Si je n'ai pas besoin de transmettre le message, je ne fais rien. Sinon je coupe ma liste en deux : j'appelle la première personne de la première moitié et je la charge de transmettre ; j'appelle la première personne de la deuxième moitié et je la charge de transmettre. — c'est exactement une fonction récursive à deux appels.

alerte.c
/* list[0] est l'appelant, déjà informé ; list[1..size-1] restent à prévenir */
static void phoneAlarm(ListRecord_t const list[], size_t size)
{
    if (size <= 1u) {                   /* cas de base : personne à prévenir */
        return;
    }
    size_t const rest  = size - 1u;
    size_t const half1 = rest / 2u;     /* moitié gauche du reste */
    size_t const half2 = rest - half1;  /* moitié droite = le reste, pas (size-1)/2 */

    if (half1 > 0u) {                   /* une moitié vide n'a pas de premier */
        showCalledPerson(&list[1]);
        phoneAlarm(&list[1], half1);
    }
    if (half2 > 0u) {
        showCalledPerson(&list[1u + half1]);
        phoneAlarm(&list[1u + half1], half2);
    }
}

Les deux gardes half1 > 0 et half2 > 0 ne sont pas décoratives. Quand le reste vaut 1, half1 = 0 : sans garde, on appellerait deux fois la même personne — une fois comme « première de la moitié gauche », une fois comme « première de la moitié droite ». Avec les gardes, chaque personne est appelée exactement une fois, et le total vaut size − 1.

Deux pièges de l'énoncé 1.14

La mauvaise formule pour la seconde moitié. Écrire halfright = (size - halfleft - 1) / 2 perd des personnes : le brouillon de l'énoncé n'appelle que 2, 3, 4, 5, 7, 10 et 11. La seconde moitié doit être le reste : half2 = rest - half1.

Le numéro de Gyro. "877-764-2532-999" fait exactement 16 caractères dans un char[16] : gcc l'accepte, mais il n'y a pas de '\0' final, et printf("%s") lit au-delà du tableau. Afficher avec %.16s ou agrandir le champ.

Combien d'appels pour 16 entrées, et pour une seule ?
15 appels pour 16 entrées, car chacun prévient exactement size−1 personnes. Et zéro appel pour une entrée : size <= 1 est le cas de base. Le nombre d'appels ne dépend pas de la forme de l'arbre, seulement de la taille.
06
récursion multiple

Fibonacci : la récursion double à chaque nœud

La suite de Fibonacci est définie par f(n) = f(n−1) + f(n−2) avec f(1) = f(2) = 1. Deux appels récursifs par appel, donc un arbre et non une chaîne : c'est la récursion multiple, et c'est là que le coût change de nature.

fibonacci.c
/* version naïve : fidèle à la définition, mais elle recalcule */
uint64_t FibRecursion(uint32_t n)
{
    if (n <= 2u) {                 /* deux cas de base : f(1) et f(2) */
        return 1u;
    }
    return FibRecursion(n - 1u) + FibRecursion(n - 2u);
}

Pour f(5), l'arbre contient neuf nœuds, donc neuf appels : f(5) une fois, f(4) une fois, f(3) deux fois, f(2) trois fois et f(1) deux fois. Les mêmes valeurs sont recalculées indépendamment, sans que personne ne s'en souvienne.

La règle · le coût

Le nombre d'appels obéit à C(n) = C(n−1) + C(n−2) + 1, avec C(1) = C(2) = 1. Il double à peu près à chaque pas : C(10) = 109, C(20) = 13 529, C(30) = 1 664 079. La complexité est O(2ⁿ) — plus précisément en φⁿ, avec φ ≈ 1,618, mais l'ordre de grandeur est le même.

Le piège

Conclure « la récursion est lente ». f(30) itératif et f(30) récursif font le même nombre d'additions utiles ; le récursif en fait 1 664 079 fois plus. La lenteur vient de l'arbre, pas de l'appel de fonction.

Pourquoi deux cas de base f(1) et f(2) plutôt qu'un seul ?
Parce que la réduction descend de deux en deux : f(2) appelle f(1) et f(0). On arrête donc à n ≤ 2 pour ne jamais demander f(0), qui n'est pas défini dans la convention du cours. Avec un seul cas de base n == 1, la récursion ne s'arrêterait pas sur f(2) et f(0) serait appelé indéfiniment.
07
mémoïsation & LUT

Mémoïsation : calculer une fois, lire ensuite

Puisque l'arbre de Fibonacci recalcule les mêmes valeurs, la correction est simple : ranger chaque résultat la première fois, et le relire ensuite. Le cours en donne deux formes — la table précalculée de l'exercice 1.2 (LUT) et le cache rempli à l'exécution (mémoïsation).

cache.c
/* LUT : table statique, calculée à la compilation (ex 1.2 c) */
static uint64_t const cFact[] = {
    1u, 1u, 2u, 6u, 24u, 120u, 720u, 5040u, 40320u, 362880u, 3628800u,
    39916800u, 479001600u, 6227020800u, 87178291200u, 1307674368000u,
    20922789888000u, 355687428096000u, 6402373705728000u,
    121645100408832000u, 2432902008176640000u          /* 20! */
};

uint64_t Factorial_with_lut(uint32_t number)
{
    if (number >= sizeof cFact / sizeof cFact[0]) {    /* hors table */
        return 0u;
    }
    return cFact[number];                              /* O(1) */
}

/* mémoïsation : le cache se remplit à l'exécution */
enum { eCacheSize = 64 };
static uint64_t sCache[eCacheSize];
static bool     sKnown[eCacheSize];

uint64_t FibMemo(uint32_t n)
{
    if (n <= 2u)   { return 1u; }
    if (n >= eCacheSize) { return 0u; }        /* hors cache */
    if (sKnown[n]) { return sCache[n]; }       /* déjà calculé */
    uint64_t const r = FibMemo(n - 1u) + FibMemo(n - 2u);
    sCache[n] = r;                             /* on range… */
    sKnown[n] = true;
    return r;                                  /* …et on rend */
}

La règle · l'échange

La mémoïsation échange de la mémoire contre du temps. Le coût passe de O(2ⁿ) à O(n) en temps, mais demande O(n) cases en plus. La LUT pousse la logique plus loin : la table est figée à la compilation, le temps devient O(1) et la mémoire est payée une fois pour toutes.

Les deux pièges du cache

Oublier d'écrire le résultat. Lire le cache sans jamais le remplir ne change rien au coût : if (sKnown[n]) return sCache[n]; doit être suivi de sCache[n] = r;.

Un cache static garde son contenu. Il survit d'un appel à l'autre et même d'un test à l'autre : la deuxième exécution mesure un cache chaud, pas le coût réel. Il faut le vider explicitement entre deux mesures, ou le déclarer local et le passer en paramètre.

récursion ou itération

Récursion ou boucle : ce que la pile coûte

Toute récursion linéaire peut s'écrire avec une boucle, et l'inverse est vrai aussi. Le choix ne porte donc pas sur la puissance d'expression, mais sur ce qu'on accepte de payer : des trames, des appels, et parfois de la lisibilité.

La récursion terminale

Une fonction est récursive terminale (tail recursive) quand l'appel récursif est la dernière opération : il n'y a plus rien à faire au retour, donc la trame n'a plus besoin d'être conservée. On obtient cette forme en transportant le résultat partiel dans un accumulateur.

terminal.c
/* non terminale : la multiplication attend le retour */
uint64_t FactRec(uint32_t n)
{
    if (n <= 1u) { return 1u; }
    return (uint64_t)n * FactRec(n - 1u);     /* il reste un × à faire */
}

/* terminale : l'appel est la dernière instruction */
uint64_t FactTail(uint32_t n, uint64_t acc)
{
    if (n <= 1u) { return acc; }
    return FactTail(n - 1u, acc * (uint64_t)n);   /* rien après l'appel */
}
/* appel : FactTail(4, 1) -> FactTail(3, 4) -> FactTail(2, 12) -> FactTail(1, 24) */
Ce que le compilateur en fait

gcc peut transformer une récursion terminale en boucle — c'est l'élimination d'appel terminal, active à -O2. La pile cesse alors de croître et le coût rejoint celui de la boucle. Mais le standard C n'impose pas cette optimisation : le même code compilé à -O0 empile ses trames. On ne compte donc jamais dessus pour garantir qu'un programme ne débordera pas.

La règle du choix
  • Boucle quand la structure est une suite : parcourir un tableau, cumuler, compter. O(1) de mémoire, pas de limite de pile.
  • Récursion quand la structure est un arbre ou un découpage : tours de Hanoï, alerte téléphonique, parcours d'arborescence, tri fusion. Écrire la boucle équivalente demanderait une pile explicite — autant laisser le processeur la gérer.
  • Récursion + cache quand l'arbre recalcule : Fibonacci, programmation dynamique.
Le piège

Réécrire une récursion en boucle « parce que c'est plus rapide » sans mesurer. À -O2, les deux versions d'une fonction terminale ont souvent le même temps. Ce qui change vraiment, c'est la mémoire : une boucle ne débordera jamais la pile, une récursion si.

Compter les appels, pas les lignes

Pour une fonction récursive, le coût se lit dans la relation de récurrence, pas dans le nombre de lignes du code. Trois formes suffisent à couvrir le chapitre : un appel qui réduit de 1, un appel qui divise par 2, deux appels qui réduisent de 1.

La dernière ligne est celle de Hanoï et de Fibonacci naïf. Pour 64 disques, 2⁶⁴ vaut 18 446 744 073 709 551 616, soit un de plus que le plus grand uint64_t : le nombre de coups 2⁶⁴ − 1 est exactement UINT64_MAX. Un compteur uint32_t déborde dès 32 disques.

La règle · trois questions
  1. Combien d'appels par niveau ? Un : la pile est une chaîne, le coût est linéaire ou logarithmique. Deux : la pile est un arbre, le coût est exponentiel — sauf si un cache intervient.
  2. De combien la taille diminue-t-elle ? De 1 : n niveaux. Divisée par 2 : log₂ n niveaux. C'est la profondeur de la pile.
  3. Le travail est-il refait ? Si oui, le cache ramène le coût au nombre de valeurs distinctes, pas au nombre de nœuds.
Applications

La dichotomie est le O(log n) du cours : chaque comparaison élimine la moitié du tableau, donc 5 étapes pour 20 éléments et 20 pour un million. Les tris récursifs (fusion, rapide) sont en O(n log n) : log₂ n niveaux, O(n) de travail par niveau. Ces trois familles — linéaire, logarithmique, exponentielle — sont celles qu'un TE demande de reconnaître.

Combien d'appels pour l'alerte téléphonique sur 1 024 entrées ?
1 023 appels, soit size − 1 : chaque personne est appelée exactement une fois. Mais la profondeur n'est que de 10 niveaux environ, log₂ 1024. C'est l'intérêt du découpage : beaucoup d'appels, peu de pile.

profondeur & pile

La profondeur de récursion a une limite

La pile n'est pas infinie : sa taille est fixée au lancement du programme, de l'ordre du mégaoctet. Une récursion qui descend de n niveaux consomme n trames ; quand la pile est pleine, l'écriture suivante touche une zone interdite et le programme s'arrête — c'est le stack overflow.

Combien de trames ?

Une trame contient les paramètres, les variables locales, l'adresse de retour et les registres sauvegardés : quelques dizaines d'octets pour une fonction simple, plusieurs centaines si elle déclare des tableaux locaux. C'est la variable à surveiller, pas le nombre d'appels : une fonction récursive appelée en boucle n'empile rien.

Le piège

« Ça a marché avec 10 000, donc c'est bon. » La profondeur maximale dépend du compilateur, des optimisations et du système : le même code passe à -O2 (récursion terminale transformée en boucle) et plante à -O0. Un test réussi sur une machine ne prouve pas la sûreté ; seule la borne sur n le fait.

Pourquoi l'alerte téléphonique ne déborde-t-elle jamais, même avec un million de personnes ?
Parce que chaque appel divise la liste par deux : la profondeur vaut log₂ n, soit 20 niveaux pour un million. Le nombre d'appels est grand (999 999), mais ils ne sont jamais simultanément empilés. C'est la différence entre nombre d'appels et profondeur.

La méthode de vérification

Trois questions, dans cet ordre : quel est le cas de base, et que rend-il ? la taille diminue-t-elle à chaque appel ? combien d'appels pour n = 5 ? Si les trois réponses sont nettes, le code est probablement juste. Sinon, dérouler à la main sur n = 2 ou n = 3 : c'est le plus petit cas non trivial, et c'est là que les erreurs apparaissent.

Deux confusions à ne pas faire

« Récursif » n'est pas « répétitif ». Appeler une fonction récursive dans une boucle ne fait pas grandir la pile : chaque appel repart de zéro, et la profondeur reste celle de la fonction. Une boucle n'ajoute aucune trame. « Profond » n'est pas « long ». Hanoï à 64 disques est très long et très peu profond ; l'alerte téléphonique à un million de personnes est très large et très peu profonde.

Checklist avant de rendre un code récursif

  • Le cas de base est écrit en premier et couvre tous les cas triviaux (0, 1, ou vide).
  • Chaque appel récursif diminue strictement la taille.
  • Chaque branche a son return.
  • Le nombre d'appels est connu pour n = 5, et vérifié à la main.
  • La profondeur maximale est bornée, et compatible avec la pile.
  • Si deux appels se répètent, un cache est prévu — et effectivement rempli.
  • Aucune variable globale ne porte l'état du calcul.
  • Le type du résultat tient la plus grande valeur attendue.
À retenir

Une fonction récursive tient en trois lignes : le cas de base, la réduction, l'appel. Tout le reste est du comptage — combien d'appels, quelle profondeur, combien de fois le même sous-problème est recalculé. Répondre à ces trois questions, c'est connaître l'algorithme.
