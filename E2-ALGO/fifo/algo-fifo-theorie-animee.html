Exercices 3.1
01
l'idée

Une file d'attente : le premier arrivé repart le premier

Le cours définit le FIFO en deux lignes : First In, First Out. Une fonction ajoute un élément, une autre retire celui qui a été ajouté en premier ; après lecture, l'élément est effacé de la liste. Rien d'autre. C'est cette contrainte, et elle seule, qui fait la file.

À retenir

Une file de caisse. On arrive derrière le dernier (la queue), on repart devant le premier (la tête). Personne ne double, personne ne sort du milieu : c'est exactement ce que garantissent put et get. Un tableau trié, lui, saurait ranger plus vite — mais ce n'est plus une file.

La règle du cours

Un FIFO, c'est deux fonctions seulement : une pour ajouter, une pour retirer le plus ancien. Tout le reste — afficher, compter, vider — se déduit d'un parcours de la liste. Si ton code permet de retirer un élément au milieu, ce n'est pas un FIFO mais une liste.

Trois confusions à tuer tout de suite
  • « FIFO = tri » : non. La file conserve l'ordre d'arrivée, pas l'ordre des valeurs. put de 3 puis 1 puis 2 sort 3, 1, 2.
  • « get lit sans retirer » : non. Dans l'énoncé 3.1, get recopie puis libère le nœud ; l'élément quitte la file. Lire sans retirer s'appelle front ou peek.
  • « FIFO veut dire tableau » : non, c'est un comportement. On l'obtient avec une liste chaînée (exercice 3.1) ou avec un tableau circulaire (section 09) ; les deux sont des FIFO.
Le vocabulaire anglais du cours

enqueue / push = put ; dequeue / pop = get ; front / head = la tête, par où l'on sort ; back / tail = la queue, par où l'on entre. Le gabarit Moodle garde les noms put et get : c'est ceux-là que le correcteur attend.

02
le modèle abstrait

Six opérations, deux invariants, quatre coûts

Avant le C, il y a le contrat. Une file expose un petit nombre d'opérations, et deux invariants qui ne doivent jamais être faux — même une microseconde. Le gabarit de l'exercice 3.1 n'en demande que quatre ; les autres se déduisent, et savoir lesquelles existent évite de réinventer la roue.

Les deux coûts de put et de size ne sont pas une imprécision : ils dépendent de ce que l'on stocke en plus du pointeur de tête. Avec la seule tête, il faut marcher jusqu'au dernier pour ajouter, et compter pour connaître la taille. Avec un pointeur de queue et un compteur, les deux deviennent instantanés (section 08).

Les deux invariants

1. Cohérence de la tête. pList == NULL si et seulement si la file est vide. Pas de nœud fantôme, pas de sentinelle dans l'exercice 3.1.

2. Fin de chaîne. Le dernier nœud a pNext == NULL, et aucun nœud n'est visité deux fois : la liste est une chaîne, jamais un cycle. C'est ce qui garantit que la boucle de put se termine.

L'idée qui tient tout

put ne choisit pas la place : c'est toujours la queue. get ne choisit pas l'élément : c'est toujours la tête. Une file n'offre aucun accès au milieu — c'est une restriction volontaire, exactement comme la pile du chapitre précédent. Tu perds la liberté d'indexer, tu gagnes deux opérations en O(1) et un ordre garanti.

Ce que le gabarit impose

Quatre prototypes, rien de plus : Data_t* createFIFO(void), bool put(Data_t** ppList, Data_t newElement), bool get(Data_t** ppList, Data_t* pElement), void showList(Data_t* pList). Les bool ne sont pas décoratifs : ils signalent l'échec (malloc refusé, file vide) sans arrêter le programme. Un correcteur regarde d'abord ça.

Pourquoi createFIFO ne prend-elle aucun paramètre et ne fait-elle qu'un return NULL ?
Parce qu'une file vide n'a aucun nœud à allouer : la valeur NULL du pointeur de tête est la file vide. Créer une file ne coûte donc rien, et malloc n'apparaît que dans put. Certaines implémentations allouent un nœud sentinelle à la création (c'est ce que fait la démo du chapitre 3 avec pBegin) ; l'exercice 3.1 ne le veut pas, et c'est plus simple.
03
la structure

La structure du cours : quatre champs, 32 octets

Tout part d'une structure de 32 octets, définie dans le gabarit Moodle. Un nœud contient une mesure — numéro de capteur, valeur, instant — et l'adresse du nœud suivant. Le champ pNext est ce qui transforme des blocs épars en liste.

Le fil unique

La variable pList de main ne contient que l'adresse du premier nœud. Le deuxième n'est joignable qu'en lisant pList->pNext, le troisième par pList->pNext->pNext. Si tu perds la tête, tu perds tout : il n'existe aucun chemin vers la liste depuis ailleurs. D'où le soin obsessionnel apporté à cette variable.

Un écart de types assumé

L'énoncé PDF écrit unsigned int sensorNumber et unsigned long time ; le gabarit Moodle et le code du cours utilisent int et long. Cette page suit le gabarit (c'est lui que tu rends), et les valeurs d'exemple restent positives : aucun piège de conversion.

Pas de sentinelle ici

La démo du chapitre 3 alloue un nœud factice au départ (pBegin = malloc(...)) : la liste n'est jamais vraiment vide. L'exercice 3.1 fait l'inverse : liste vide = NULL. Ne mélange pas les deux modèles — dans le gabarit, un « premier nœud » factice serait un élément de plus dans la file, et un get de trop.

04
put

put : allouer, remplir, puis accrocher en queue

Ajouter en queue demande trois choses dans cet ordre : demander la mémoire, la remplir, puis seulement toucher à la liste. Si l'allocation échoue, la file doit rester exactement dans l'état où elle était. Voici le code du cours, complet.

put — ajout en queue (ex3-1_fifo.c)
bool put(Data_t** ppList, Data_t newElement)
{
   /* 1) créer la mémoire */
   Data_t* pNew = (Data_t*)malloc(sizeof(Data_t));
   if (pNew != NULL)
   {
      /* 2) recopier la valeur reçue dans le bloc alloué */
      *pNew = newElement;
      pNew->pNext = NULL;
      /* 3) file vide ou non ? */
      if (*ppList == NULL)
      {
         *ppList = pNew;          /* file vide : le nœud devient la tête */
      }
      else
      {
         Data_t* pFlow = *ppList;
         while (pFlow->pNext != NULL)   /* jusqu'au dernier */
         {
            pFlow = pFlow->pNext;
         }
         pFlow->pNext = pNew;     /* on accroche derrière le dernier */
      }
      return true;
   }
   return false;
}

Trois points méritent d'être lus lentement. D'abord, *pNew = newElement copie les 32 octets de la structure, pNext compris — c'est pour cela que la ligne suivante le remet à NULL : le nouvel élément est en queue, il ne doit rien suivre. Ensuite, le test if (*ppList == NULL) traite le seul cas où la tête change. Enfin, la boucle while s'arrête sur le dernier nœud (celui dont pNext vaut NULL), pas sur NULL : après la boucle, pFlow est le dernier nœud, et c'est son pNext qu'on remplit.

Les trois branches de put
situationbranchece qui changecoût
file vide*ppList = pNewla tête, et rien d'autreO(1)
n ≥ 1 élémentboucle puis pFlow->pNextle pNext du dernierO(n)
malloc échouereturn falserien : la file est intacteO(1)
L'ordre des opérations est le contrat

malloc → test de NULL → copie → pNext = NULL → accrochage. Tant que malloc n'a pas réussi, on ne touche pas à la liste : un échec laisse la file utilisable. Et on n'accroche jamais avant d'avoir rempli pNext : sinon le dernier nœud pointerait vers un bloc dont le champ est encore indéterminé.

Le piège qui transforme la file en pile

Écrire pNew->pNext = *ppList; *ppList = pNew; est plus court, plus élégant, et faux : c'est une insertion en tête, donc un LIFO. Tu obtiens C, B, A. Le seul cas où cette version serait correcte est… une file d'un seul élément. C'est le genre de faute qui passe les tests à un élément et échoue à l'examen.

Le cast de malloc

Le cours écrit (Data_t*)malloc(sizeof(Data_t)), le code compile en C11 avec ou sans cast. Garde la forme du cours : elle est explicite, et c'est celle que le gabarit utilise. En revanche, ne remplace jamais sizeof(Data_t) par 32 écrit à la main.

05
get

get : détacher la tête, recopier, libérer

Retirer le premier est le geste le plus simple du chapitre : la tête est déjà connue. Trois lignes suffisent, mais leur ordre décide si le programme fonctionne ou s'il utilise un bloc libéré. Voici la version du cours, telle quelle.

get — retrait en tête (ex3-1_fifo.c)
bool get(Data_t** ppList, Data_t* pElement)
{
   /* a) la file est-elle vide ? */
   if (*ppList == NULL)
   {
      return false;
   }
   else
   {
      /* b) mémoriser la tête, la sortir, recopier, libérer */
      Data_t* ToDel = *ppList;
      *pElement = *ToDel;
      *ppList = ToDel->pNext;
      free(ToDel);
      return true;
   }
}

Quatre instructions, quatre responsabilités distinctes. ToDel garde l'adresse du nœud à détruire, sinon on la perdrait en avançant la tête. *pElement = *ToDel recopie les 32 octets vers l'appelant — c'est le seul moment où les données existent encore. *ppList = ToDel->pNext fait avancer la tête, éventuellement vers NULL. free(ToDel) rend le bloc au tas.

La règle : recopier avant de libérer

Après free(ToDel), le bloc n'existe plus : lire ToDel->sensorValue serait un usage après libération, comportement indéfini. Toute lecture doit donc précéder le free. Et get doit rendre false — pas planter, pas afficher — quand la file est vide : c'est un cas normal, pas une erreur.

Le pNext recopié : le piège caché du gabarit

*pElement = *ToDel copie aussi pNext. L'élément rendu à l'appelant contient donc l'adresse du nœud suivant… que free vient de détruire. Si l'appelant range cet élément et lit element.pNext plus tard, il suit un pointeur suspendu. La correction tient en trois lignes :

variante sûre — recopier les champs, pas la structure entière
      Data_t* pOld = *ppList;
      *ppList = pOld->pNext;              /* la tête avance d'abord */

      pElement->sensorNumber = pOld->sensorNumber;
      pElement->sensorValue  = pOld->sensorValue;
      pElement->time         = pOld->time;
      pElement->pNext        = NULL;       /* jamais pOld->pNext */

      free(pOld);
      return true;

Cette variante est celle que documente la fiche de révision du cours. Elle a un second mérite : elle rend visible ce qui sort de la file. Trois champs de données, pas quatre — pNext est de la mécanique interne, il n'appartient pas à l'élément rendu.

Coût et cas particulier

get est en O(1) : aucune boucle, quel que soit le nombre d'éléments. Le cas « un seul élément » n'est pas particulier dans le code : ToDel->pNext vaut NULL, donc *ppList devient NULL et la file est vide — exactement ce qu'il faut.

Lire sans retirer n'existe pas ici

Si tu veux seulement regarder la tête, n'appelle pas get : tu détruirais le nœud. Écris if (*ppList != NULL) { *pElement = **ppList; pElement->pNext = NULL; } — c'est le front du modèle abstrait, et il ne touche pas à la liste.

laboratoire · liste chaînée

Séquence complète : put A, B, C puis get A, B

La séquence de l'énoncé, pas à pas, avec les adresses symboliques du tas (0x3000, 0x3020, 0x3040) et le pointeur de tête sur la pile (0x2000). Chaque état est réel, y compris les nœuds libérés.

Ce que montre le laboratoire

Trois put ont coûté 0, 0 puis 1 saut : le coût grandit avec la longueur. Deux get ont coûté exactement la même chose, quel que soit le nombre de nœuds : O(1). Et aucun nœud n'est resté alloué après son retrait.

Deux détails importants

Le pNext d'un nœud libéré contient encore 0x3020 : la mémoire n'est pas effacée, elle est seulement rendue. La moindre lecture après free lirait cette valeur — c'est le pointeur suspendu. Et le nœud libéré reste dessiné en pointillés : il est inutile de le « nettoyer », il faut seulement ne plus le toucher.

Après les deux get, combien de nœuds sont alloués sur le tas ?
Un seul : C (0x3040). A et B ont été libérés par free. Le nombre de malloc réussis moins le nombre de get réussis donne toujours le nombre de nœuds vivants — ici 3 − 2 = 1.
07
Data_t **

Data_t** : pour changer la tête de l'appelant

Une fonction C reçoit toujours une copie. Si put recevait un simple Data_t*, elle modifierait sa copie du pointeur et la tête de main resterait NULL : les nœuds seraient alloués, chaînés… et perdus. D'où le double pointeur, présent dans les deux prototypes qui modifient la file.

l'appel et la signature
Data_t* pList = createFIFO();     /* dans main : la tête */

if (!put(&pList, element)) { /* échec : plus de mémoire */ }
if (!get(&pList, &element2)) { /* échec : file vide      */ }

/* put reçoit l'ADRESSE de pList, donc un Data_t** */
bool put(Data_t** ppList, Data_t newElement);
bool get(Data_t** ppList, Data_t* pElement);
Lire les expressions du double pointeur

La règle

Une fonction qui doit changer la valeur d'une variable de l'appelant reçoit l'adresse de cette variable. Pour changer un int, on passe int* ; pour changer un Data_t*, on passe Data_t**. showList, qui ne fait que lire, reçoit Data_t* : c'est le signe qu'elle ne modifie pas la file.

Ce que le compilateur t'empêche déjà de faire

put(pList, element) ne compile pas : pList est un Data_t *, le paramètre attend un Data_t ** — incompatible. C'est une chance : le type du prototype documente le contrat. En revanche, si tu écrivais toi-même bool put(Data_t* pList, ...), tout compilerait, et pList = pNew ne changerait rien chez l'appelant. La faute serait silencieuse.

Et si la file est vide ?

ppList reste valide : c'est l'adresse de pList, qui existe toujours. C'est *ppList qui vaut NULL. C'est pourquoi put teste *ppList == NULL et non ppList == NULL. Tester ppList ne protégerait que du cas où l'appelant passe NULL — ce que le gabarit ne fait jamais, mais le cours le mentionne.

08
variante · pointeur de queue

put en O(1) : mémoriser aussi la queue

Le parcours de put est le seul coût linéaire de la file. Il disparaît si l'on garde, à côté de la tête, l'adresse du dernier nœud. C'est la variante que la fiche de révision mentionne comme « hors gabarit » : le principe est au programme, le code ne l'est pas. Mais c'est exactement ce que fait un vrai buffer embarqué.

variante hors gabarit — une structure pour la file
typedef struct
{
   Data_t* pHead;   /* premier nœud : par où l'on sort */
   Data_t* pTail;   /* dernier nœud  : par où l'on entre */
} FIFO_t;

bool put(FIFO_t* pFifo, Data_t newElement)
{
   Data_t* pNew = (Data_t*)malloc(sizeof(Data_t));
   if (pNew == NULL) return false;

   *pNew = newElement;
   pNew->pNext = NULL;

   if (pFifo->pHead == NULL)   /* file vide */
   {
      pFifo->pHead = pNew;
      pFifo->pTail = pNew;
   }
   else                        /* accrocher derrière la queue */
   {
      pFifo->pTail->pNext = pNew;
      pFifo->pTail = pNew;
   }
   return true;
}

Deux écritures au lieu d'un parcours : pTail->pNext = pNew accroche, pTail = pNew déplace la queue. Aucune boucle, donc O(1) quel que soit le nombre d'éléments. Le prix à payer est une seconde variable à maintenir exactement — et c'est get qui pose problème.

get correspondant — attention au dernier élément
bool get(FIFO_t* pFifo, Data_t* pElement)
{
   if (pFifo->pHead == NULL) return false;   /* file vide */

   Data_t* pOld = pFifo->pHead;
   pFifo->pHead = pOld->pNext;               /* la tête avance */

   pElement->sensorNumber = pOld->sensorNumber;
   pElement->sensorValue  = pOld->sensorValue;
   pElement->time         = pOld->time;
   pElement->pNext        = NULL;

   free(pOld);

   if (pFifo->pHead == NULL)                 /* la file vient de se vider */
   {
      pFifo->pTail = NULL;                   /* sinon la queue est suspendue */
   }
   return true;
}

Le piège du dernier get

Oublier pTail = NULL quand la file se vide laisse la queue sur un bloc libéré. Le put suivant écrira dans pTail->pNext — un usage après libération, souvent silencieux en test et fatal en production. Les deux pointeurs forment un couple : tout ce qui touche à l'un doit vérifier l'autre.

Ce que la variante change pour l'examen

Le gabarit impose les prototypes à double pointeur : tu dois savoir écrire put(Data_t**, Data_t) et expliquer son O(n). La variante à structure FIFO_t est la réponse à la question « comment faire mieux ? » — pas le code à rendre. Sache la décrire en deux phrases : « on garde l'adresse du dernier nœud, on accroche derrière lui, et on remet la queue à NULL quand la file se vide ».

09
tableau circulaire

Le tableau circulaire : deux index, un modulo

Pas de malloc, pas de pNext : un tableau de N cases, deux index qui avancent, et un modulo pour revenir au début. Le FIFO devient un anneau : la case qui vient d'être lue sera la prochaine écrite, sans jamais déplacer les données. C'est la structure des buffers UART et des files d'événements.

anneau.c — la version C11, hors gabarit
#define RING_N 8

typedef struct
{
   Data_t  buf[RING_N];
   size_t  readIndex;    /* prochaine lecture */
   size_t  writeIndex;   /* prochaine écriture */
} Ring_t;

bool ringPut(Ring_t* pRing, Data_t newElement)
{
   size_t next = (pRing->writeIndex + 1) % RING_N;
   if (next == pRing->readIndex) return false;   /* plein */

   pRing->buf[pRing->writeIndex] = newElement;
   pRing->writeIndex = next;
   return true;
}

bool ringGet(Ring_t* pRing, Data_t* pElement)
{
   if (pRing->readIndex == pRing->writeIndex) return false;  /* vide */

   *pElement = pRing->buf[pRing->readIndex];
   pElement->pNext = NULL;
   pRing->readIndex = (pRing->readIndex + 1) % RING_N;
   return true;
}
Les trois états de l'anneau
étatconditionconséquence
videreadIndex == writeIndexget rend false
partielreadIndex != writeIndex, cas généralon lit et on écrit normalement
plein(writeIndex + 1) % N == readIndexput rend false, rien n'est écrit
Pourquoi N − 1 et pas N ?

Avec N cases et seulement deux index, « plein » et « vide » auraient la même apparence : dans les deux cas readIndex == writeIndex. On sacrifie donc une case : tant que l'index d'écriture n'a pas rejoint l'index de lecture, il reste une place libre. Capacité utile = N − 1. Pour utiliser les N cases, il faut un compteur count en plus (ou un drapeau) — et une section critique si un ISR s'en mêle.

Trois pièges d'anneau
  • Écrire avant de tester : si buf[writeIndex] = newElement précède le test de saturation, on écrase la case de lecture et la file perd un élément. Tester d'abord, écrire ensuite.
  • Index non signés : readIndex-- sur un size_t égal à 0 donne un très grand nombre, puis un accès hors tableau. On n'utilise que + 1 et le modulo.
  • % coûte cher : sur un petit microcontrôleur sans division matérielle, % N se paie. Si N est une puissance de deux, (i + 1) & (N - 1) donne le même résultat en un cycle.
Le compromis, en une phrase

La liste s'adapte à la demande mais alloue et libère à chaque opération ; l'anneau a une capacité fixe mais ne fait aucune allocation après l'initialisation. Pour un flux régulier connu à l'avance, l'anneau gagne ; pour une file qui grandit sans borne, la liste gagne.

La suite des lectures est exactement la suite des écritures : A, B, C, D, E, F, G, H, I. Le bouclage des index ne change pas l'ordre, il ne fait que réutiliser la mémoire. Et le refus de put quand l'anneau est plein est une information, pas un plantage : c'est la contrepartie de la capacité fixe.

Le piège : écrire avant de tester

Dans l'état plein, WR vaut 0 et RD vaut 1. Si tu écris d'abord dans buf[0], tu détruis la dernière valeur non lue (ici A, déjà sortie, mais dans un autre scénario ce serait une donnée vivante) et WR rattrape RD : la file paraît vide alors qu'elle vient de perdre un élément. Tester puis écrire, jamais l'inverse.

Avec N = 8, combien d'éléments peut-on stocker au maximum ? Et avec un compteur count ?
Sept avec la règle RD == WR / (WR+1)%N == RD : une case est sacrifiée. Huit avec un champ count maintenu à chaque put et get, car count distingue alors le plein du vide sans perdre de place. Le prix : une variable de plus à mettre à jour, et une section critique si un ISR partage l'anneau.

comparaison

Liste chaînée ou tableau circulaire : choisir sans se tromper

Les deux structures rendent le même service — un ordre FIFO — et ne coûtent pas la même chose. La question n'est pas « laquelle est la meilleure », mais « est-ce que je connais la taille maximale, et est-ce que je peux allouer pendant le fonctionnement ? ».

La règle de choix

Contraintes temps réel ou taille bornée → tableau circulaire : pas d'allocation, pas de fragmentation, latence constante. Taille inconnue ou très variable → liste chaînée : elle grandit jusqu'à la mémoire disponible, au prix d'un malloc par élément et d'un parcours pour put.

Pourquoi le cours commence par la liste

Parce qu'elle montre malloc, free et les pointeurs — le programme du chapitre 3. L'anneau, lui, n'utilise que des index : c'est un tableau, donc du chapitre 1. Savoir passer de l'un à l'autre, c'est savoir ce que coûte réellement une file.

L'erreur de comparaison

« La liste est O(n) donc elle est mauvaise » : faux. get est O(1) dans les deux cas, et un put O(n) sur une file de dix éléments coûte dix sauts — souvent moins qu'un malloc. Ce qui compte, c'est le débit et la taille de ta file, pas le tableau des complexités seul.

Un UART reçoit 115 200 bauds, soit environ 11 520 octets par seconde. Quelle structure pour le buffer de réception ?
Un anneau de taille fixe (par exemple 64 ou 256 octets, puissance de deux pour le masque), alloué une fois. L'ISR de réception écrit avec WR, le programme principal lit avec RD : aucune allocation dans l'interruption, latence bornée, et un débordement se détecte proprement (put rend false). Une liste chaînée avec malloc dans un ISR est une très mauvaise idée.

Le détail qui compte en embarqué

Un anneau partagé entre une ISR et la boucle principale n'a pas besoin de verrou si un seul producteur écrit writeIndex et un seul consommateur écrit readIndex : chaque index n'a qu'un écrivain. Déclare-les volatile (le compilateur ne doit pas les garder en registre), écris le tableau avant d'avancer l'index, et n'utilise jamais de malloc dans l'interruption.
